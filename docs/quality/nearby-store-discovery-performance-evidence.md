# Nearby store query plan and latency evidence

## Measurement condition

- Date: 2026-08-07
- Reproduce with `scripts/perf/nearby-store-search.sh`, which runs `NearbyStoreDiscoveryBenchmark`
  (`BEANFLOW_BENCHMARK=true`). The benchmark is excluded from the normal suite.
- Database: PostgreSQL 17.5 with PostGIS 3.5 (`postgis/postgis:17-3.5` Testcontainers),
  `USE_GEOS=1 USE_PROJ=1 USE_STATS=1`. JVM 21.0.11.
- Host: Apple Silicon workstation (`Mac OS X aarch64`), Docker limited to 2 CPUs and 8 GB. The
  image publishes a `linux/amd64` manifest only, so **the container ran under emulation**. Absolute
  times are not representative of a native amd64 runtime and are not an SLA or a capacity figure.
- Dataset: generated by a closed formula, not `random()`, so re-running reproduces the same rows.
  Store `i` is placed at
  `lon = 126.80 + ((i * 7919) mod 100000) / 100000 * 0.40`,
  `lat = 37.35 + ((i * 6421) mod 100000) / 100000 * 0.30`,
  a deterministic pseudo-uniform spread over a 0.40° × 0.30° box around the query point. Every
  store is `accepting_orders` and `pickup_enabled`. The 100,000-row scale is the 10,000-row scale
  plus 90,000 more rows from the same formula. `VACUUM ANALYZE` ran before each capture.
- Fixed query conditions: query point `(127.0, 37.5)`, `radiusMeters = 1000`, page limit `100`
  (`LIMIT 101` including the next-page probe), 20 warm-up iterations, 200 measured iterations.
- Latency is measured in the JVM around the production repository call over a single reused
  connection, so it covers query execution, driver round trip and row mapping, but not connection
  establishment.

## Actual result

| Scale | First-page rows | Plan shape | Planning | Execution (EXPLAIN) | Shared buffers |
|---|---:|---|---:|---:|---:|
| 10,000 profiles | 27 | `Bitmap Index Scan on idx_store_discovery_profile_location` → `Bitmap Heap Scan` → `Nested Loop` → `Sort` (quicksort) | 33.953 ms | 51.615 ms | 209 hits |
| 100,000 profiles | 101 (full page) | same access path, `Sort` becomes `top-N heapsort` | 34.403 ms | 56.035 ms | 1,585 hits |

| Scale | p50 | p95 | p99 | min | max | samples |
|---|---:|---:|---:|---:|---:|---:|
| 10,000 profiles | 0.397 ms | 0.599 ms | 0.860 ms | 0.316 ms | 1.895 ms | 200 |
| 100,000 profiles | 1.850 ms | 2.220 ms | 2.559 ms | 1.664 ms | 2.680 ms | 200 |

Index detail at 100,000 rows: the GiST bounding-box condition
`location && _st_expand(queryPoint, 1000)` returned 451 candidate rows in 1.045 ms; the exact
spheroid `ST_DWithin` filter then removed 186, leaving 265 rows for the top-N sort.

## What this does and does not show

- **Shown:** the production predicate reaches the V33 GiST index at both scales, and it is the
  bounding-box index condition — not a sequential scan — that bounds the candidate set. Ten times
  more data increased first-page latency roughly 4.7× (0.397 ms → 1.850 ms p50) while the plan shape
  stayed the same apart from the sort switching to top-N heapsort. Growth here is driven by the
  number of rows *inside* the radius, which grew from 27 to 265 candidates, not by the total table
  size.
- **The planner chose a bitmap path, not a plain index scan.** The benchmark records the access
  method rather than forcing one, and no index was added or changed to make a number look better.
- **`EXPLAIN` execution time is far higher than the measured latency** (51.6 ms versus 0.397 ms p50
  at 10,000 rows). `EXPLAIN (ANALYZE)` adds per-node instrumentation that is disproportionately
  expensive under emulation. Treat the plan capture as shape evidence and the repeated-iteration
  distribution as the latency evidence; do not mix the two numbers.
- **Not a comparison against a baseline.** There is no prior implementation measured under the same
  conditions, so no improvement is claimed.
- **Not measured:** native amd64 timings, concurrent request load, RPS, error rate under load, GC
  and allocation, connection-pool behaviour, multi-page cursor traversal cost, non-uniform or
  clustered store distributions, and scales beyond 100,000 profiles.

## An earlier measurement artefact, corrected

The first run reported `p50 = 117.936 ms` at 10,000 rows. That run used `DriverManagerDataSource`,
which opens a new connection per call, so almost all of the time was TCP connect and authentication
rather than query cost. The benchmark now reuses one connection. The 117.936 ms figure is recorded
here only so it is not mistaken for a regression against the current numbers.

## Revisit when

Re-run the fixed fixture after changing the select list, the sort tuple, the index definition, the
radius contract, the public maximum page size, or the PostgreSQL/PostGIS version. Capture a native
amd64 baseline and a concurrent-load profile before making any SLA, capacity or throughput claim.
