## 1. 무엇을 만드는가

고객이 검색창 하나에 입력한 문자열로 매장을 찾는다. 검색 대상은 네 가지다.

| 대상 | 예 | 데이터 출처 |
|---|---|---|
| 매장명 | `강남역점` | `merchant_store_discovery_profile.name` (기존) |
| 브랜드명 | `스타벅스` | `merchant_brand.name` (**신규**) |
| 지역명 | `강남구`, `역삼동`, `감정리` | `merchant_region` 법정동 4계층 (**신규**) |
| 메뉴명 | `아메리카노` | `merchant_menu.name` (기존, 매장 단위 조회만 존재) |

결과는 항상 **매장 카드 한 종류**이며, 검색어에 걸린 메뉴가 있으면 매장당 최대 3개를 함께
내려준다. `"강남 스타벅스"`처럼 단어가 여러 개면 각 단어가 서로 다른 속성에 걸려도 같은 매장이
결과가 된다.

이 작업의 성격은 "검색 API 하나 추가"가 아니라 **존재하지 않던 두 종류의 데이터(브랜드, 지역)를
정의하고, 그 위에 검색을 올리는 것**이다. 착수 시점에 브랜드는 테이블도 코드도 0이었고, 매장에는
좌표만 있고 주소가 없었다.

## 2. 대주제별 결정

### 2.1 검색 대상과 결과 단위

**문제.** 브랜드·지역이 대상에 들어오면 "결과가 매장인가, 브랜드인가, 메뉴인가"가 흐려진다.

**선택.** 결과는 언제나 매장 단위로 집계하고, 매칭 근거를 `matchReason`(term 종류 집합)과
`matchedMenus`(최대 3개)로 표시한다.

**대안과 트레이드오프.**

| 대안 | 장점 | 포기한 이유 |
|---|---|---|
| 매장만 반환 (근거 없음) | 응답이 가장 단순 | `아메리카노`로 검색했을 때 왜 이 매장이 나왔는지 알 수 없다 |
| 섹션 분리 통합검색 (매장/브랜드/메뉴 각각) | 표현력 최대 | 섹션마다 정렬·페이지네이션이 달라져 백엔드·프론트 모두 복잡도가 급증한다 |
| **매장 + 매칭 메뉴 (선택)** | 응답 스키마 하나, 근거 표시, 페이지네이션 단순 | 페이지 확정 후 메뉴 2차 조회가 필요하다 |

**대가.** 쿼리가 1단계(매장 페이지 확정) + 2단계(메뉴 미리보기)로 나뉜다. 2단계는 최대 50개
매장 ID로 제한되므로 비용은 유계다.

**메뉴 검색은 매장 경계를 가로지른다.** 색인 테이블이 매장별로 분할되지 않으므로 `아메리카노`
검색은 반경 안의 **전 매장 메뉴**를 한 번에 훑는다. 매장을 순회하며 각각 조회하는 구조가 아니다.
기존 `merchant_menu`가 `(store_id, name, id)` 인덱스라 매장 단위 조회만 가능했던 것과 반대다.

```text
1) discovery_store_search_term 토큰 매칭   → 매장 후보 (매장 무관, GIN trigram)
2) merchant_store_discovery_profile 조인   → ST_DWithin 반경 필터 (GiST)
3) openOnly/pickupAvailable 필터와 정렬    → page + scan-boundary cursor
4) 확정 page의 매장 ID로 matchedMenus 2차 조회
```

`GET /stores/{storeId}/menus`([ADR-076](../adr/ADR-076-store-catalog-read-contract.md))는 한 매장의
전체 카탈로그 조회이고 이 경로는 매장을 가로지르는 검색이다. 목적과 계약이 다르며 서로를 대체하지
않는다. 반경 상한은 기존 nearby 계약을 승계해 `10000`m다.

**의도적으로 만들지 않은 것: 메뉴 단위 결과.** `아메리카노 4,500원 · A카페 0.3km`처럼 메뉴가
결과 행이 되는 가격 비교형 목록은 제공하지 않는다. 커서 튜플이 `(가격, 메뉴ID)` 같은 것으로 바뀌고
한 매장이 여러 행으로 중복되므로 페이지네이션·중복 제거 규칙이 통째로 달라진다. 필요해지면 별도
결정으로 연다.

### 2.2 텍스트 매칭 엔진

**문제.** 한국어 매장명·메뉴명은 짧은 고유명사가 많다. `스타`로 `스타벅스`가 나와야 하고,
`스태벅스`(오타)도 구제되면 좋다.

**선택.** PostgreSQL `pg_trgm`을 쓰되 **substring 우선 + 유사도 보완의 하이브리드**다.
토큰별로 case-insensitive substring을 먼저 적용하고, substring으로 걸리지 않은 토큰에만
유사도 `0.3` 이상 매칭을 추가한다.

**대안과 트레이드오프.**

| 대안 | 장점 | 포기한 이유 |
|---|---|---|
| `LIKE '%q%'`만 | 확장·인덱스 불필요 | 인덱스를 못 써서 데이터 증가에 선형 열화. 오타 불가 |
| PostgreSQL FTS (`tsvector`) | 표준, 랭킹 내장 | 한국어 형태소 분석기 없이 `simple` 설정은 어절 단위라 `스타`→`스타벅스`가 안 걸린다 |
| 순수 `pg_trgm` 유사도 | 매칭 경로 하나, 구현 단순 | `스타`(2자)와 `스타벅스 강남역점`(10자)의 유사도가 낮아 **정확한 부분 검색이 오히려 실패**한다 |
| Elasticsearch | 검색 품질 최상, 확장성 | 색인 동기화·재색인·장애 fallback이 전부 새 운영 대상이 된다. 현재 데이터 규모에서 이득보다 실패 모드 추가가 크다 |
| **하이브리드 (선택)** | 정확 검색은 예측 가능하게, 오타만 추가 구제 | 쿼리에 경로가 둘이라 복잡도와 테스트가 늘어난다 |

**대가.** 매칭 경로가 둘이라 "왜 이게 나왔는가"를 설명할 때 두 규칙을 봐야 한다. 대신 substring
경로의 결과가 결정적이라 회귀 테스트가 안정적이다.

**함정 하나.** `%` 연산자의 임계값은 세션 GUC `pg_trgm.similarity_threshold`에 의존한다. 세션
설정에 결과가 흔들리지 않도록 쿼리 안에서 `similarity(...) >= 0.3`을 **명시적으로 다시 비교**한다.

### 2.3 다중 토큰 의미론

**문제.** `"강남 스타벅스"`는 한 문자열인가, 두 조건인가.

**선택.** 공백으로 분리한 최대 5개 토큰의 **AND**. 각 토큰이 그 매장의 term 중 적어도 하나에
매칭돼야 한다. `강남`은 지역에, `스타벅스`는 브랜드에 걸리면 통과한다.

**대안.** 통짜 문자열 substring은 거의 항상 0건이 된다(`"강남 스타벅스"`라는 문자열을 가진 필드가
없으므로). OR는 결과가 많지만 관련 없는 것이 대부분 섞인다.

**의도적으로 만들지 않은 것.** `강남`을 지역 필터로 자동 승격하는 파서. 토큰은 전부 동등하게
전체 term 집합에 대해 평가된다. 파서를 두면 "어떤 단어가 지역으로 인식되는가"라는 숨은 규칙이
생기고, 지역명과 같은 이름의 매장(`강남집`)에서 어긋난다.

### 2.4 정렬과 페이지네이션

**문제.** 좌표가 선택 사항이므로 정렬 규칙이 하나로 정해지지 않는다. 또 관련도 점수는 실수인데,
이 저장소의 페이지네이션은 서명된 keyset cursor(ADR-070)다.

**선택.**

- `sort=relevance`(기본) / `sort=distance`를 클라이언트가 고른다. `distance`는 좌표 필수.
- 관련도를 **정수로 양자화**한다: `relevanceRank = 1_000_000 - floor(relevance × 1_000_000)`.
- 정렬 튜플을 전부 오름차순으로 맞춘다: `(relevanceRank, distanceMicrometers, storeId)`.

**왜 양자화인가.** 부동소수를 cursor에 그대로 넣으면 동점 판정이 page 경계에서 흔들려 항목 누락과
중복이 생긴다. 정수로 고정하면 keyset 비교가 결정적이다. 이는 새로 만든 기법이 아니라 기존
근접 검색이 거리에 쓰던 `distanceMicrometers`와 같은 방식이라, 코드와 테스트 패턴을 재사용한다.

**왜 내림차순을 뒤집어 오름차순으로 만드는가.** SQL의 row 비교(`(a,b) > (?,?)`)는 방향이 섞이면
쓸 수 없다. `1_000_000 - x`로 뒤집으면 관련도 내림차순을 오름차순 튜플 하나로 표현할 수 있어
기존 all-ASC keyset 규칙을 그대로 쓴다.

**대가.** 정렬 경로가 둘이라 구현·테스트가 2배가 되고, cursor scope도 `sort` 값에 따라 둘로 나뉜다
(같은 검색어라도 정렬을 바꾸면 이전 cursor는 400이어야 한다).

### 2.5 검색 데이터 구조 — 이 설계의 중심

**문제.** 검색 대상 텍스트가 매장 프로필, 브랜드, 지역, 메뉴 네 테이블에 흩어져 있다. 매 요청
4-way 조인 위에 유사도를 계산하면 GIN 인덱스가 사실상 무력화된다.

**선택.** 매장당 "검색 가능한 문자열"을 한 행씩 모은 색인 테이블 `discovery_store_search_term`을
두고, **브랜드·지역 쓰기 커맨드와 같은 트랜잭션에서 동기 갱신**한다.

```text
discovery_store_search_term
  store_id | term_kind        | term_normalized | weight | source_id
  ---------|------------------|-----------------|--------|----------
  S1       | STORE_NAME       | 강남역점         | 1.00   | NULL
  S1       | BRAND_NAME       | 스타벅스         | 0.90   | NULL
  S1       | REGION_SIGUNGU   | 강남구           | 0.80   | NULL
  S1       | MENU_NAME        | 아메리카노       | 0.70   | M7

  S2       | REGION_EUPMYEONDONG | 동면          | 0.80   | NULL
  S2       | REGION_RI        | 감정리           | 0.80   | NULL
```

토큰 하나가 인덱스 조회 하나가 되고, AND는 `HAVING COUNT(*) = <토큰 수>`로 표현된다.

**대안과 트레이드오프.**

| 대안 | 장점 | 포기한 이유 |
|---|---|---|
| 조인 직접 | 유지할 색인 없음, 항상 최신 | 오타 허용을 위해 전체 행에 `similarity`를 돌려야 해 인덱스 무력화 |
| 배치 주기 갱신 | 쓰기 경로 단순, fan-out 없음 | 이름을 바꿔도 검색에 안 잡히는 **stale 결과**가 생긴다. 이 저장소의 명시적 실패 원칙과 충돌 |
| 매장당 한 행에 전체 텍스트 연결 | 행 수가 적음 | `similarity`가 문자열 길이에 희석돼 메뉴가 많은 매장이 부당하게 낮은 점수를 받는다 |
| **term 테이블 동기 갱신 (선택)** | 인덱스 친화적, stale 없음 | 유지 대상이 하나 늘고, 브랜드명 변경이 소속 매장 수만큼 fan-out 쓰기가 된다 |

**fan-out 대가와 그 처리.** 브랜드명을 바꾸면 소속 매장의 `BRAND_NAME` term을 모두 갱신해야
한다. 같은 트랜잭션이므로 소속 매장이 많으면 긴 잠금이 생긴다. **비동기 큐로 우회하지 않고**
소속 매장 1000개를 상한으로 두고 초과 시 `409`로 명시적으로 거절한다. 상한에 도달하면 그때
배치 설계를 ADR로 다시 결정한다.

**초기 적재는 migration SQL이 할 수 없었다 (구현하면서 발견).** 색인 테이블을 만드는 migration이
기존 매장·메뉴를 그대로 채우는 것이 자연스러워 보였고 계획도 그렇게 적혀 있었다. 문제는
`term_normalized`가 **질의가 만드는 문자열과 정확히 같아야** 한다는 것이다. 검색은 질의 토큰을
Kotlin `SearchTextNormalizer`로 정규화한 뒤 색인과 비교하므로, 색인이 다른 규칙으로 만들어졌다면
그 매장은 오류 없이 그냥 검색되지 않는다.

SQL 백필은 Kotlin 함수를 부를 수 없어 `normalize(NFKC) + lower() + 공백 축약`으로 다시 구현해야
한다. 두 경로에 같은 입력을 넣어 비교하는 테스트를 먼저 만들어 확인했더니 두 건이 갈렸다.

| 입력 | PostgreSQL `lower()` | Kotlin `lowercase()` |
|---|---|---|
| `İSTANBUL` | `istanbul` | `i̇stanbul` (`U+0069 U+0307`) |
| `ΟΔΟΣ` | `οδοσ` | `οδος` (어말 시그마) |

Java의 `String.lowercase()`는 Unicode SpecialCasing과 어말 시그마 조건을 적용하고 PostgreSQL의
`lower()`는 적용하지 않는다. 문자를 하나씩 치환해 맞출 수도 있지만, 그러면 Unicode 규칙이 늘 때마다
**실패 없이** 어긋나는 코드가 하나 더 생긴다. 그래서 두 번째 구현 자체를 두지 않고 초기 적재를
애플리케이션 재색인으로 옮겼다(MD-2026-018). 대가는 migration 직후 색인이 비어 있다는 것이고,
그 상태는 커버리지 gauge가 `0`으로 드러낸다.

### 2.6 브랜드 데이터 모델

**선택.** `merchant`가 소유하는 독립 Aggregate `merchant_brand`. 매장은 `brand_id`로 **ID 참조**
하며 JPA 객체 연관관계와 cascade를 만들지 않는다. `brand_id`는 nullable이다.

**대안과 트레이드오프.**

| 대안 | 장점 | 포기한 이유 |
|---|---|---|
| 프로필에 `brand_name` 텍스트 컬럼 | 가장 저렴, 검색 즉시 동작 | `스타벅스`/`스타벅스코리아` 중복을 못 막고, 이름 변경 비용이 매장 수에 비례한다. 나중에 Aggregate로 승격할 때 전수 정제가 필요 |
| 브랜드 제외 | 범위 축소 | 프랜차이즈 검색이 제품 요구의 핵심이다 |
| 브랜드 필수화 | 조인·색인 단순 | 개인 카페마다 1:1 브랜드가 생겨 브랜드 개념이 매장 별칭으로 퇴화 |

**nullable인 이유.** 브랜드 없는 개인 카페가 정상 상태다. 필수화하면 데이터 모델이 거짓말을 한다.

### 2.7 지역 데이터 모델

**선택.** 행정안전부 **법정동 코드 10자리** 폐쇄 어휘 `merchant_region`. 매장주는 신규 생성 없이
기존 코드를 선택만 한다. `region_code`는 백필 후 `NOT NULL`로 승격한다.

**대안과 트레이드오프.**

| 대안 | 장점 | 포기한 이유 |
|---|---|---|
| 자유 텍스트 3칸 | 시드 불필요, 마이그레이션 가벼움 | `강남구`/`강남 구` 표기 흔들림을 못 막는다. 지역 필터·집계로 재사용 불가 |
| 좌표에서 역지오코딩 | 입력 부담 0 | 외부 Provider 의존이 생겨 실패 정책·timeout 설계가 통째로 추가되고, Provider 장애 시 매장 등록이 막힌다 |
| 운영자가 쓰는 지역만 등록 | 시드가 수십 행 | 신규 지역 매장마다 운영자 선행 작업이 병목이 된다 |
| **법정동 전체 시드 (선택)** | 표기 통일, 필터·통계 재사용 | 시드 약 2만 행(SQL 약 2MB)이 저장소에 들어간다 |

**세부 하나.** 세종특별자치시처럼 시군구 계층이 없는 행정구역이 있어 `sigungu`/`eupmyeondong`/`ri`는
`NOT NULL DEFAULT ''`다. `NULL`을 쓰지 않는다.

**구현하면서 바뀐 것: 3계층 → 4계층.** 설계 단계에서는 시도·시군구·읍면동 3계층으로 정했다.
실제 시드를 적재하고서야 **폐지되지 않은 20,560행 중 15,209행(74%)이 리 단위**라는 것이 드러났다.
3계층으로는 `감정리`에 있는 매장이 `동면`으로만 찾히고 `감정리`로는 찾히지 않는다. 시드의 4분의 3에
해당하는 구멍이라 한계로 남기지 않고 `ri` 열과 `REGION_RI` term 종류를 추가했다.

리 행의 `eupmyeondong`은 상위 읍·면 이름을 **그대로 둔다.** 리 이름으로 덮어썼다면 검색 가능 범위가
넓어지지 않고 이동만 했을 것이다. 리 이름의 전국 중복(`상리`, `신촌리`)은 좌표·반경 필터가 이미
거르므로 별도 식별자를 두지 않았다. 계층 판별에 새 자료도 필요 없었다 — 법정동 코드 뒤 2자리가
곧 리 코드다.

| 리 모델링 대안 | 장점 | 포기한 이유 |
|---|---|---|
| 리 행을 시드에서 제외 | 시드가 4분의 1로 줄어든다 | 리에 주소를 둔 매장이 **고를 코드 자체가 없다.** `NOT NULL` 승격 시 커버리지 마이그레이션이 실패해 배포가 막힌다 |
| 리 이름을 `eupmyeondong`에 덮어쓰기 | 새 열·새 term 종류 불필요 | 읍·면 이름으로는 못 찾게 되어 범위가 넓어지지 않고 이동한다. 열 이름과 내용도 어긋난다 |
| **`ri` 열 + `REGION_RI` 추가 (선택)** | 읍·면과 리 양쪽으로 검색된다 | term 종류가 여섯에서 일곱으로 늘고 리 매장의 term이 3행에서 4행이 된다 |

**왜 `NOT NULL` 승격인가.** 지역이 빈 매장은 지역명 검색에서 **조용히 사라진다.** 기존
`merchant_store_discovery_profile`이 V33→V34로 쓴 것과 같은 fail-closed 커버리지 gate 패턴을
그대로 따른다: 컬럼 생성 → 값 입력 → 별도 마이그레이션이 `SET NOT NULL`로 검증.

### 2.8 권한과 쓰기 주체

**선택.** 브랜드는 운영자(`PLATFORM_OPERATOR`), 지역은 해당 매장의 `STORE_OWNER`.
`STORE_STAFF`는 지역을 바꿀 수 없다.

**근거.** 두 데이터의 성격이 정반대다. **브랜드는 여러 매장이 공유하는 자원**이라 매장이 스스로
유명 브랜드에 편입될 수 있으면 사칭 문제가 된다. **지역은 매장 하나에 붙는 사실**이라 소유자가
가장 정확히 알고 공유 자원이 아니므로 사칭 위험이 없다.

**대가.** 권한 경로가 두 갈래라 인가 테스트가 늘어난다.

### 2.9 위치 처리와 프라이버시

기존 [ADR-020](../adr/ADR-020-nearby-location-privacy.md)/BR-28을 그대로 승계한다. 정밀 좌표는
요청 처리 중에만 쓰고 DB, 캐시, AuditRecord, 로그, trace, metric 어디에도 저장하지 않으며
cursor에도 원문을 넣지 않는다(해시만 넣는다).

**검색어도 같은 취급이다.** 검색어와 토큰을 저장하지 않는다. 색인 테이블에 저장되는 것은 매장의
공개 속성이지 사용자가 입력한 검색어가 아니다.

**"설정 주소지"를 서버에 저장하지 않기로 했다.** 설계 중 "저장된 주소지 인근 검색" 요구가
제기됐고, BR-28의 Revisit Condition("위치 기반 개인화에 대한 명시적 동의와 보존 정책이 도입될 때")에
해당하는지 검토한 뒤 **승격하지 않기로 결정**했다.

| 대안 | 서버가 저장하는 것 | 반경 검색 | 대가 |
|---|---|---|---|
| **A. client storage (선택)** | 없음 | 정확히 됨 | 주소지가 기기·브라우저에 묶이고 storage를 지우면 사라진다 |
| B. 법정동 코드만 저장 | `region_code` (동 단위) | 반경 대신 행정구역 일치 | 동 경계 바로 밖 매장이 빠진다 |
| C. 정밀 좌표 저장 | 위·경도 | 정확히 됨 | ADR-020 개정 + 동의·보존·삭제 정책 필요 |

A를 고른 이유는 **요구를 서버 보존 없이 그대로 충족할 수 있기 때문**이다. 개인정보 보존 면적을
늘리지 않고 공개 API 계약도 바뀌지 않는다(좌표는 원래 요청마다 받는다). 기기 간 동기화가 실제
요구가 되면 그때 B나 C로 승격하며, 그 판단은 [MD-2026-017](../decisions/minor-decisions.md)과
ADR-020의 2026-08-15 평가 절에 기록되어 있다.

**구현상 승계할 것.** 쿼리 파라미터를 raw `String`으로 바인딩하고 애플리케이션이 직접 검증한다
(MD-2026-008). 프레임워크 변환 오류 메시지가 좌표를 응답·로그로 흘리지 않게 하기 위함이다.

### 2.10 실패 의미론

이 저장소의 원칙(`AGENTS.md`, ADR-009)을 검색에 적용한 결과다.

| 상황 | 결과 |
|---|---|
| `pg_trgm` 부재, 색인 조회 실패, DB 장애 | `503`. **빈 목록이나 순차 검색으로 대체하지 않는다** |
| 색인 갱신 실패 | 원 커맨드 트랜잭션 전체 rollback. 부분 성공 없음 |
| 재색인 중 일부 매장 실패 | 성공 수와 실패 매장 ID를 응답에 담고 부분 실패를 성공으로 보고하지 않음 |
| 결과 0건 | `200` 빈 배열. 정상이며 장애와 구분한다 |
| 슬롯 counter 손상 | pickup 불가 `false`가 아니라 `503` |

**닫힌 매장을 기본으로 숨기지 않는 이유도 같은 맥락이다.** 이름을 알고 검색했는데 0건이 나오면
사용자는 그것을 고장으로 읽는다. 상태는 `open`/`pickupAvailable` 플래그로 표시하고 필터는
선택으로 둔다.

## 3. 새로 도입하는 기술

| 기술 | 용도 | 도입 비용 | 대안 대비 |
|---|---|---|---|
| PostgreSQL `pg_trgm` extension | trigram 유사도와 GIN 인덱스 | 확장 설치 + Flyway migration. 권한 없으면 **migration 실패**(fallback 없음) | Elasticsearch 대비 새 운영 대상·동기화 실패 모드가 없다 |
| GIN trigram 인덱스 | `term_normalized` 검색 가속 | 인덱스 크기와 쓰기 비용 증가 | B-tree로는 부분 일치를 가속할 수 없다 |
| 법정동 코드 시드 데이터 | 지역 폐쇄 어휘 | 약 2만 행, SQL 약 2MB. 생성 스크립트 유지 | 자유 텍스트 대비 표기 통일과 재사용성 |

**도입하지 않는 것과 그 이유.** Elasticsearch, Redis 캐시, 형태소 분석기, 자동완성 엔진, ML 랭킹,
그리고 **고객 위치 저장소**. 앞의 다섯은 "현재 데이터 규모에서 얻는 이득보다 새로 떠안는 실패
모드가 크다"가 공통 근거이고, 마지막은 "서버 보존 없이 요구를 충족할 수 있다"가 근거다.
`pg_trgm`이 목표 지연을 만족하지 못한다고 **측정된 뒤에** 재검토한다.

## 4. 아키텍처에 생기는 변화

### 4.1 Merchant 모듈 최초의 쓰기 경로

착수 시점에 `merchant` 모듈에는 `@PostMapping`/`@PutMapping`/`@PatchMapping`/`@DeleteMapping`이
**하나도 없었다.** 매장과 메뉴는 데모 시드와 테스트 fixture로만 생성됐다. 브랜드 명령과 지역
명령이 이 모듈 최초의 쓰기 엔드포인트가 된다.

### 4.2 모듈 순환 의존과 그 회피

색인 갱신은 `merchant → discovery`, 검색의 매장 상태 조회는 `discovery → merchant`다. 그대로 두면
Spring Modulith 구조 검증이 순환 의존으로 깨진다.

```text
변경 전:      discovery ──조회──> merchant

순진한 확장:  discovery <──조회──> merchant        (순환, 검증 실패)
                        ──갱신──

선택한 구조:  merchant ──의존──> shared/api (StoreSearchIndexOperations)
                                      ▲
                                      └── discovery/internal 이 구현
              discovery ──조회──> merchant        (기존 방향 유지)
```

port를 `shared/api`에 선언하고 `discovery/internal`이 구현한다. `merchant`는 `shared`에만
의존하고 `discovery`를 모른다.

### 4.3 읽기 전용이던 Discovery에 쓰기 상태가 생긴다

`discovery`는 지금까지 순수 조회 모듈이었다. 색인 테이블을 소유하면서 처음으로 유지해야 하는
상태가 생긴다. 대신 그 상태는 파생 데이터이며 source of truth가 아니다. 재색인으로 언제든 원본에서
다시 만들 수 있다.

### 4.4 계약 표면 확장

cursor endpoint 4개(`stores-search-relevance`, `stores-search-distance`, `operations-brands`,
`regions`)가 ADR-070 registry에 추가된다. 기존 `/stores/search` 목표 계약은 `sort`, `openOnly`,
`matchedMenus` 추가로 개정된다. 고객 위치 관련 계약은 바뀌지 않는다.

## 5. 알면서 감수한 한계

측정 없이 "충분하다"고 주장하지 않기 위해, 설계 단계에서 이미 아는 한계를 명시한다.

1. **색인 신선도의 구멍.** 매장·메뉴 쓰기 API가 없으므로 시드나 직접 DML로 매장명·메뉴가 바뀌면
   색인이 자동으로 따라가지 않는다. 브랜드·지역만 동기 갱신되고 나머지는 운영자 재색인 커맨드가
   필요하다. 이 구멍을 숨기지 않기 위해 커버리지 gauge와 runbook 점검 쿼리를 둔다. 정식 해소책은
   매장·메뉴 쓰기 API가 생길 때 그 커맨드가 색인 갱신을 흡수하는 것이다. **색인 테이블 migration
   직후에도 색인은 비어 있다**(2.5의 정규화 문제). 운영자가 재색인을 실행하기 전까지 커버리지
   gauge는 `0`이고, 그 창이 관측 가능한 것이 이 설계가 제공하는 보장이다.
2. **텍스트 품질 상한.** 부분 일치 + 제한적 오타 구제 수준이다. 형태소 기반 검색, 동의어,
   자동완성은 없다.
3. **브랜드 fan-out 상한 1000.** 그 이상은 제품 기능이 아니라 명시적 거절이다.
4. **상권 별칭 미지원.** `홍대`, `가로수길`은 법정동 명칭이 아니라 검색되지 않는다. 법정동 체계
   **안**의 단위인 리는 4계층 개정으로 검색되지만, 체계 밖의 상권 이름은 여전히 별도 자료가 필요하다.
5. **관련도 가중치는 근거 없는 추정값.** `1.00/0.90/0.80/0.70`은 순서 관계만 의도한 초기값이며
   실제 검색 품질로 검증된 값이 아니다. 그래서 ADR이 아닌 Minor Decision(MD-2026-015)으로 두어
   되돌리기 쉽게 했다.
6. **설정 주소지가 기기에 묶인다.** client storage에만 있으므로 다른 기기·브라우저에서 다시
   설정해야 하고 storage를 지우면 사라진다. 개인정보를 저장하지 않는 대가다.
7. **반경 상한 10km.** 기존 nearby 계약을 승계한 값이며 그 이상은 계약 변경이 필요하다.

| `pg_trgm` 부재 시 동작 | extension 제거 상태에서 `503`이고 빈 목록이 아닌지 | Not run |
| 커버리지 gate | 지역 미입력 매장이 있을 때 migration 실패 | Not run |
| 모듈 순환 의존 | Spring Modulith 구조 검증 | 통과. `merchant ↔ discovery` 순환 없음 |
| 프라이버시 회귀 | 검색어·좌표·주소지가 DB/log/metric tag/trace에 없음 | Not run |

## 7. 다시 볼 조건

- `pg_trgm` 조회가 목표 지연을 만족하지 못한다고 **측정될** 때 → 외부 검색 엔진 재검토
- 자동완성·오타 교정이 실제 요구가 될 때
- 브랜드 fan-out이 1000 상한에 도달할 때 → 배치 갱신 설계를 ADR로
- 매장·메뉴 쓰기 API가 생길 때 → 색인 동기 갱신 흡수, 재색인 커맨드의 역할 축소
- 상권 별칭 검색이 요구될 때 → 별칭 사전의 운영 주체부터 결정 (리는 4계층 개정으로 해소됐다)
- 실제 검색 로그가 쌓일 때 → term 가중치와 유사도 임계값 재조정
- 주소지의 기기 간 동기화가 요구될 때 → BR-28 Revisit Condition에 따라 ADR-020 재개
- 메뉴 단위 가격 비교 목록이 요구될 때 → 커서 튜플과 중복 매장 처리를 새로 결정

## 8. 결정 순서에 대한 메모

이 기능의 결정은 다음 순서로 진행했고, 순서 자체가 설계에 영향을 줬다.

1. **제품 질문 먼저** — 결과 단위, 좌표 필수 여부, 브랜드/지역의 존재 여부. 여기서 "브랜드와
   지역이 아예 없다"가 드러나 작업 성격이 "검색 추가"에서 "데이터 모델 신설 + 검색"으로 바뀌었다.
2. **기존 결정 확인** — [ADR-103](../adr/ADR-103-store-search-strategy.md)이 이미 `Accepted`로
   매장명·메뉴명 검색을 결정해 둔 것을 발견했다. 매칭 방식·정렬·페이지 상한 6개 항목이 새 요구와
   충돌했다. `AGENTS.md`의 Source conflicts 절차에 따라 임의 선택 대신 충돌을 보고하고, ADR을
   먼저 개정한 뒤 계획을 갱신했다.
3. **데이터 모델** — 브랜드/지역의 소유권·어휘·쓰기 주체.
4. **검색 구조** — 데이터가 네 곳에 흩어진 것이 확정된 뒤에야 색인 테이블이 필요하다는 결론이
   나왔다. 순서를 바꿨다면 색인 설계를 먼저 하고 데이터 모델에 끼워 맞췄을 것이다.
5. **계약 세부** — cursor scope, 상한값, 필터 파라미터.
6. **프라이버시 경계** — "설정 주소지" 요구가 뒤늦게 나왔을 때, 기능을 먼저 설계하지 않고
   **기존 프라이버시 결정을 먼저 읽었다.** ADR-020이 이미 "사용자 검색 좌표 장기 저장"을 검토하고
   기각한 상태였고, 그 덕에 요구를 서버 보존 없이 충족하는 A안을 먼저 검토할 수 있었다.

7. **데이터를 실제로 적재한 뒤 모델을 고쳤다** — 지역 어휘를 3계층으로 정한 것은 법정동 자료의
   실제 구성을 모르는 상태의 결정이었다. Milestone 1에서 시드를 넣고 나서야 74%가 리 단위라는
   것과, 세종특별자치시에 시도 자리 행이 없고 시군구가 두 단어인 행이 있다는 것이 드러났다.
   문서상 설계로는 나올 수 없고 실제 데이터를 통과시켜야만 나오는 종류의 사실이라, 계획을
   그대로 밀지 않고 ADR을 다시 열어 4계층으로 고쳤다.

8. **불변식을 지키려다 계획된 구현 방법을 버렸다** — "정규화는 색인과 질의가 같은 함수를 쓴다"는
   불변식을 먼저 정해 두었기 때문에, migration SQL 백필이 그 불변식을 깨는 두 번째 구현이라는
   것이 눈에 들어왔다. 두 경로를 비교하는 테스트를 먼저 짜서 실제로 갈리는 입력을 확인했고
   (2.5), 그제야 백필의 위치를 옮겼다. 불변식이 없었다면 백필은 통과했을 것이고, 문제는
   `İ`나 `Σ`가 든 이름을 가진 매장이 검색되지 않을 때에야 드러났을 것이다.

기존 결정을 먼저 읽지 않고 3~6을 진행했다면 Accepted ADR을 코드로 우회하는 결과가 됐을 것이다.
반대로 7과 8은 문서만으로는 알 수 없었던 것이라, 구현 중 드러난 사실로 결정을 되돌리는 경로도
함께 열어 두어야 한다는 것을 보여준다. 둘의 차이도 있다. 7은 데이터를 넣어 봐야 알 수 있었고,
8은 **불변식을 미리 적어 둔 덕분에** 검증 대상이 무엇인지 알 수 있었다.
