# BeanFlow Product Overview

## Problem

카페 선주문 거래는 메뉴와 금액을 저장하는 것만으로 끝나지 않는다.

- 픽업 시간의 매장 수용량을 초과하면 안 된다.
- 마지막 재고를 여러 고객에게 동시에 판매하면 안 된다.
- 같은 쿠폰과 포인트를 두 주문에서 동시에 사용하면 안 된다.
- 외부 결제가 성공했지만 서버가 결과를 기록하지 못할 수 있다.
- 픽업 완료 이후 포인트 적립과 정산이 중복되거나 누락될 수 있다.
- 확정 정산 뒤 환불이 발생해도 과거 결과를 임의로 덮어쓰면 안 된다.
- 알림 실패가 주문 성공으로 숨겨지거나 주문 자체를 롤백해서도 안 된다.

BeanFlow는 이 거래 생명주기를 명시적인 도메인 모델, 트랜잭션 경계, 멱등성, 조정 원장과 운영 복구 절차로 다룬다.

## Product Goal

고객, 매장과 플랫폼 운영자가 하나의 거래 사실을 서로 다른 관점에서 신뢰할 수 있게 한다.

### Customer

- 영업 중이며 픽업 가능한 매장을 찾는다.
- 현재 가격·재고·픽업 슬롯을 기준으로 주문한다.
- 쿠폰과 포인트를 적용하고 중복 없이 결제한다.
- 매장의 접수·제조·준비 상태를 확인한다.
- 픽업 완료 후 적립 내역을 확인한다.

### Store

- 메뉴, 영업시간, 픽업 수용량과 판매 재고를 관리한다.
- 결제된 주문을 수락·거절하고 제조 상태를 변경한다.
- 매출, 환불, 혜택 비용과 예상 정산을 확인한다.
- 정산 항목에 이의를 제기한다.

### Platform Operations

- 결제 결과 불명, 알림 실패와 정산 차이를 추적한다.
- correlation ID, event ID와 감사 로그로 거래 흐름을 재구성한다.
- 안전한 reconciliation과 재처리를 실행한다.
- 수동 조정의 주체와 사유를 남긴다.

## Initial Scope

- 회원·매장 권한
- 매장·메뉴·옵션·영업시간
- 위치 기반 매장 검색
- 픽업 슬롯과 판매 재고 예약
- 주문 가격 스냅샷
- 쿠폰과 포인트
- 모의 PG 기반 멱등 결제와 부분 환불
- 주문 접수·제조·준비·완료
- 준비 완료 알림
- 일별 내부 정산, 조정 원장과 이의제기
- 기초 매출 분석
- 감사 로그와 운영자 재처리

## Success Criteria

초기 제품은 다음을 자동화된 검증으로 보여야 한다.

- 같은 결제 요청이 중복 승인되지 않는다.
- 슬롯·재고·쿠폰이 경합 상황에서 한도를 초과하지 않는다.
- 결제 결과가 불명확하면 성공 또는 실패로 위장하지 않는다.
- 확정 정산 이후 환불은 Adjustment로 기록된다.
- 중복 이벤트로 포인트·정산·알림이 중복 처리되지 않는다.
- 의존성 장애가 암묵적 로컬 fallback으로 숨겨지지 않는다.
- 실제 PostgreSQL에서 매핑, 제약, SQL과 동시성을 검증한다.

## Constraints

- 초기 배포 구조는 DDD 기반 Modular Monolith다.
- Kotlin, Spring Boot, Spring MVC, Spring Data JPA와 PostgreSQL을 기본으로 한다.
- Redis와 Kafka는 필요성과 장애 정책을 증명한 뒤 도입한다.
- 외부 PG와 알림은 Port/Adapter로 격리한다.
- 실제 자금, 카드 원문과 가맹점 계좌 지급을 다루지 않는다.
